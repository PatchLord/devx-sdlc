# Open questions

The frontier. What we know we do not know, so "how far through are we" has a number instead of a
feeling. A question leaves this file by being answered, by being deferred with a reason, or by being
declared not worth answering.

**Status:** `open` · `deferred` · `answered` (with where the answer landed) · `dropped` (with why).

| D1 | Is 300 lines the right ceiling? | Judgement. What should be measured is the size at which reviewers stop finding anything. | open — E5 |
| D2 | Would mob elaboration beat our async handover? | Refuted as a doc edit; genuinely open as a way of working. Needs one trial, not an argument. | open |
| D3 | What would agent identity look like for us? | We have none. Sessions are anonymous and commit as a human. Fine with one supervised session, not fine beyond that. | open |
| D4 | Is two-reviewers-at-High workable via two CODEOWNERS entries? | Believed yes; never tried. There is no per-path approval count. | open |
| D5 | Is mutation testing worth its cost at High? | Currently *to build* and deliberately not first. | deferred until B1–B4 |
| D6 | Does the deskilling effect appear in our own numbers? | Three external sources say it should. Number 5's who-found-it split is a weak instrument for it. | open |
| D7 | Should we add structural tests — file-length caps, enforced layer dependency direction, one canonical implementation of shared helpers? | A class of check we do not have. The rationale is context efficiency rather than tidiness: an agent in a codebase where every corner looks alike carries transferable understanding, and its output becomes predictable. Needs per-project values, which is why it is a question. Reported to work at a frontier lab on a 1M-line codebase. | open |
| D8 | One review agent with several persona lenses, or several agents? | We ship one. The reported practice is one agent per persona — front-end architect, reliability, scalability — each primed with that persona's written standards, triggered on every push. Our own sources support the shape: four reviewer bots on one codebase never agreed on a single finding, so lenses find different things. Unknown for us: cost per pull request, and whether dismissal rates stay under the threshold when several agents comment. | open |
| D9 | Should garbage collection also run automatically? | We adopted the scheduled human hour. The source also runs background agents that scan for deviations, grade quality and open small refactoring pull requests, most reviewable in under a minute and automerged. Automerging agent-authored refactors is a bigger step than anything we currently allow, and it interacts with the protected set. | open |
| D10 | Should the depth grade be derived from the diff rather than set once by a human in the SOW? | ADS-1 computes a consequence class from a committed path manifest plus CODEOWNERS, recomputes it at PR time from the real diff, and lets CI raise it and block. Ours is a human judgement made at the moment of least information, and only the *review* half is per-diff for us via CODEOWNERS. Its own concession is that the design rests on the manifest being complete, so it trades a wrong-in-both-directions guess for a silent gap. Both failure modes are real; we have no evidence about which is worse here. | open — see finding 44 |
| D11 | Should hand-computed expected values be required on the protected set regardless of novelty? | Ours keys "expected values computed by hand, not by the model that wrote the code" to **novelty** (05-depth), a judgement we admit nobody can measure. The property that predicts damage is **consequence**, which is derivable from CODEOWNERS. ADS-1 keys its equivalent to consequence and pre-authorises extending it downward on escape-point evidence; we have no such trigger. | open |
| D12 | Should the standing agent context name the paths where a mistake is unrecoverable? | `devx-starter/CLAUDE.md`'s "protected set" is the **gate** set — tests, thresholds, CI config, CODEOWNERS, criteria — and never names payments, auth, personal data or migrations. Those live only in CODEOWNERS, which the agent never reads. So the agent's standing context is silent about exactly the paths where being wrong is unrecoverable. ADS-1 compiles its manifest into a generated, delimited block of root CLAUDE.md with a CI staleness check, which looks cheap and tier-1. Not yet through refutation. | open |
| D13 | Is there any cap on serial human latency, or only on the cost of asking? | ADS-1 hard-caps serial pre-code human approvals at 1/2/3 by size, self-approval counting as one, and declares that exceeding the cap is a defect in the standard rather than a discipline failure in the engineer. It also budgets verification by where it runs — local pre-commit p90 under 90s, PR CI under 20 minutes, nightly unbounded — and forbids local hooks from calling a SaaS API. We make asking free and grade requests, which is a different axis. We have no latency budget anywhere. | open |

## Client and contractual risk — the category neither standard covers

Raised by ADS-1's "missing categories" and verified absent from our own 20 documents on 6 August 2026. The
first two are the class of failure that ends a client relationship rather than costing a sprint.

| # | Question | Why it matters | Status |
|---|---|---|---|
| R1 | What may an agent READ and transmit? | Our documents govern what an agent may write and say nothing about client source, customer records, logs or production dumps going to a third-party model. No per-engagement AI-use matrix checked against each MSA or DPA — several client agreements restrict subprocessors or require disclosure. No repo allowlist, no secret or personal-data redaction in prompts and session transcripts, no retention or residency position. `02-before-build.md` puts named third-party AI processing with written client permission in the SOW, which is the beginning of an answer and not the whole of one. | open |
| R2 | Licence, copyleft and originality warranties on generated code | No licence-compatibility or copyleft scan, no detection of verbatim third-party reproduction in generated hunks, and no position on the originality warranties client contracts routinely carry — "all deliverables are original work, free of third-party IP". A generated 3,000-line client is exactly the artefact our review rules wave through. `grep -riE "licen[cs]e\|copyleft\|SPDX"` over `docs/` returns nothing on this subject. ADS-1 names the hole and does not fix it either. | open |
| R3 | Is provenance disclosure in a client repository engineering's decision to make? | An `Assisted-By:` trailer in a client-owned repository is a permanent, discoverable disclosure that AI authored their deliverable. ADS-1 mandates the trailers and then flags this in its own missing-categories section with no resolution. Whether provenance lives in the client repo or an internal side-table keyed by commit SHA is a contracts question, not a tooling one. | open |
| R4 | Exposure control where we do not own the pipeline | The sharpest thing in ADS-1 that we have no answer to. On a live Shopify theme or a client-controlled pipeline, **merge IS exposure**, so any gate written against flag enablement evaporates on precisely the client surfaces it was written for. Our `promote.yml` and the release checklist assume we own the pipeline. Concretely: on a repo where merge is exposure, which of the five required checks changes, and what does "Rollback tested, not assumed" mean — because today it means nothing there. | open |
| R5 | Who becomes able to review? | Our binding constraint is non-author reviewer attention, and every artefact that used to teach judgement — spec, plan, tests, PR narrative, decision record — is agent-drafted by rule. `14-limits.md` cites the survey (16% of senior engineers say juniors fully understand what they submit) and provides no mechanism: no metric for newly qualified reviewers, no funded shadow review, no declared fraction of work done human-authored with the agent read-only. ADS-1's proposed fix is unbuilt process. | open |
| R6 | How is the agent used during an incident? | Break-glass covers bypassing a gate. Nothing covers agent permissions at 3am, whether production logs or customer data may be pasted into a session, whether an agent may run remediation against production, who reads the diff when the reviewer is asleep, or how AI-assisted remediation is reconstructed in the post-incident review. | open |
| R7 | Conformance levels for repos we do not control | Our runbook assumes every repo can take branch protection, CODEOWNERS, CI and a sub-90-second affected-test subset. Real client work includes repos with no tests, no CI, client-controlled pipelines where we cannot set protection, and repos we contribute to but do not own. Needed: which gates are mandatory where we do not control the host, what compensating controls substitute, and what we refuse outright — plus a written exception criterion so a non-conforming engagement is a recorded decision rather than a silent hole. | open |
| D14 | What is the written response to a flaky test on a required check? | `grep -rniE "flak\|quarantin\|intermittent\|rerun"` over all 20 documents returns one incidental hit, and it lists `.skip(` as a **gate weakening** — so our only written position on a flake forbids the only remedy we name. No flake-rate metric, no quarantine with an owner and an expiry, no rule about a check that is red one run in six. A live project hits this squarely and does not solve it either: its context file documents two specs that fail under a shared test schema and instructs "don't fix them by weakening assertions", which is prose. Elsewhere in the same repo somebody had time to root-cause one properly — a per-request listen/close cycle, "24 consecutive clean runs after, 3 failures in ~30 before" — which is what the real answer looks like and does not scale to every flake. | open |
| D15 | Does a design system need a tier-1 form, and what is it? | Our entire treatment is one bullet about design tokens; the starter has nothing. A live project invests heavily — twenty always-true design rules in standing agent context, a doctrine declared the theme source of truth, a 48-line pre-push guard — and **still lost the case that mattered**: a 69-file feature commit disabled four accessibility lint rules, and form labels were fixed nineteen days later. So the doctrine-in-context half demonstrably does not hold on its own, and the one mechanical guard covers naming rather than any doctrine rule. Open: which design rules are expressible as a lint at all, and whether the honest answer is that a design system is a tier-2 review criterion with a named artefact. Bears directly on the loudest complaint about our own prototype. | open |
| D16 | What keeps a plan document that reproduces code from becoming a regression generator? | The sharpest observation in that repo: a review fix was applied to a test block in a plan document while the implementation recipe 200 lines later still showed the pre-fix code — so following the plan verbatim would fail its own test, with three further stale recipes in the same file each reproducing a defect that review had just closed. Our `docs/design/` and `docs/specs/` templates invite exactly this shape, `17-artefacts.md` classifies them as living, and nothing checks a code block in a document against the code. Their remedy is a manual grep-per-pattern sweep — prose enforcing prose. Open: whether a doc-code drift check is cheaply buildable (fenced blocks tagged with a source path, one CI grep), or whether the rule is that plan documents never contain code. | open |
